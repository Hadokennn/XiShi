# 整体架构

## 一、三层 Agent 架构

```
┌─────────────────────────────────────────────┐
│  Concierge Agent（主调度，唯一入口）          │
│  - 接收原始输入                              │
│  - 路由到分区（一条可属多个分区）             │
│  - 跨分区/跨天关联                           │
│  - 装订每日手帐布局                          │
└─────────────────────────────────────────────┘
                  ↓ 派单
┌─────────────────────────────────────────────┐
│  分区 Worker（无状态的"开荒工人"）            │
│  灵感 / 亲子 / 心情 / …                      │
│  - 各自独立的 prompt（用户可维护）            │
│  - 各自独立的开荒模式（拓展/追问/共情）       │
│  - 不持有记忆，按需向记忆层请求               │
└─────────────────────────────────────────────┘
                  ↕ 共享
┌─────────────────────────────────────────────┐
│  统一记忆层（Single Source of Truth）        │
│  - 所有 Agent 读同一份                       │
│  - 数据模型见 data-model.md                  │
└─────────────────────────────────────────────┘
```

### 为什么不直接把分区做成 subagent

直觉上"分区 = subagent"很顺，但这会撞上**跨分区/跨天关联**的命门——subagent 的本质是 context 隔离，一旦育儿 worker 和灵感 worker 各管各的记忆，"今天孩子又因为同样的事情发脾气"就调不到 3 周前那条育儿记录了。

正确的分层是：**分区 worker 只负责"加工动作"，记忆是全局的**，由 Concierge 按需切片喂给 worker。这样既保留了"分区有独立人格、独立 prompt"，又不丢"第二大脑能跨分区关联"。

### 各 Agent 的职责

| Agent | 状态 | 输入 | 输出 |
|-------|------|------|------|
| **Concierge** | 全局上下文 | 原始 Atom / 时间触发 | 路由决策、关联查询、装订指令 |
| **分区 Worker** | 无状态 | 单条/几条 Atom + 切片记忆 | Cultivation（开荒产物） |
| **记忆层** | - | CRUD 请求 | 实体 + 向量检索结果 |

## 二、五层记忆模型

按**时间衰减 × 内容性质**两个维度切分，**不是按"内容性质"单维度切**（避免和分区维度混淆）。

| 层 | 时间尺度 | 装什么 | 谁写 | 谁读 |
|----|----------|--------|------|------|
| **Buffer**（此刻） | 当前 session | 用户正在输入的这一条 | 输入入口 | Concierge |
| **Today**（此页） | 当天 | 今日所有 Atom + 已开荒的 Cultivation | Concierge | Concierge 装订手帐 |
| **Zone**（此区） | 近 N 天（衰减） | 分区相关的事件、模式、未闭环的线索 | 分区 worker 写产物 | 分区 worker 开荒时调用 |
| **Episodic**（事件） | 长期 | 结构化的「场景-反应-反思-策略」四元组 | AI 草拟 + 用户确认 | 跨天关联、主动提醒 |
| **Soul**（此人） | 永久 | 你是谁、价值观、长期模式、在意的人 | AI 提案 + 用户必须 accept | 全局人格基底，所有 Agent 共享 |

### 关键设计

- **Episodic 是育儿场景的命脉**——普通日记 app 没有这层，产品差异化的核心
- **Soul 必须 propose → accept**——AI 偷偷写 Soul 是信任灾难
- **Soul 有半衰期**：3 个月没 review 的 entry 会被弱化或提醒确认
- **跨层检索**：向量 + 关键词 + 时间衰减组合

## 三、AI 工作流

### 实时通路（白天，毫秒级）

```
用户扔一条 → Concierge 接住 → 写入 Atom（status=raw）
            → 轻量分类（zone_ids + confidence）
            → 简短确认反馈（"接住了，归到了亲子区"）
```

**实时通路只做"接住"，不做开荒**。理由：
- 开荒成本高（多次 LLM 调用 + 检索），实时跑会慢、贵、还可能打扰用户
- 用户白天的目标是"扔进来不漏"，不是"立刻看到 AI 想法"

### 异步通路（晚上，批处理）

```
用户主动触发 / 定时（例如 22:00）
  ↓
Concierge 取出今日所有 Atom
  ↓
按分区分组，派发给对应 Worker
  ↓
分区 Worker 调用记忆层（Zone + Episodic + Soul）→ 生成 Cultivation
  ↓
Concierge 收回所有 Cultivation → 跨分区关联 → 装订今日 Page
  ↓
（亲子区）AI 草拟可能的 Episode（status=draft）
  ↓
（每周日）AI 提案 Soul 更新（status=proposed）
  ↓
push 通知用户「今日手帐已装订」
```

## 四、分区开荒模式（MVP：3 个分区）

每个分区有自己的"开荒姿势"——这是产品的灵魂，不是 prompt 模板可以草草打发。

### 灵感区 — **拓展 + 关联**

| 输入 | 输出 |
|------|------|
| "我想做一个能记录灵感的 app" | • 3 个延伸方向（产品形态、目标用户、差异化）<br>• 历史相关 idea 关联（"3 周前你提过类似的"）<br>• 一句"值不值得做"的判断<br>• 关键问题清单（让你下次能继续深入） |

**心态**：兴奋、扩展、刺激思考。

### 亲子区 — **苏格拉底式追问**

| 输入 | 输出 |
|------|------|
| "今天小宝因为饼干碎了崩溃大哭，我吼了她" | • 3 个反思问题（"她的反应是不是另有原因？""你当时的情绪是什么？""你希望她从这件事学到什么？"）<br>• 历史相似事件关联<br>• 「下次策略」草稿（用户可编辑） |

**心态**：温和、不评判、引导思考。**不能直接给"你应该怎么做"的建议**——会引发抗拒。

### 心情区 — **共情 + 镜像（不给建议）**

| 输入 | 输出 |
|------|------|
| "今天加班到 11 点，整个人空空的" | • 复述 + 情绪命名（"你今天感到一种很深的疲惫和空虚"）<br>• 一句轻问候<br>• **关键追问**：「你想被陪着，还是想被解决？」 |

**心态**：陪伴。心情区给建议会让人崩溃，**这是产品哲学的红线**。

> ⚠️ **MVP 不做待办区**——市面上待办 app 太多，做不出差异化，反而稀释产品定位。等 MVP 跑通后视情况再补。

## 五、输入入口

### MVP 支持的模态

| 模态 | 必须 | 说明 |
|------|------|------|
| **语音** | ✅ | 命脉。半夜胡思乱想、陪孩子时双手不空 |
| **文字** | ✅ | 地铁/会议/精确表达 |
| **图片** | ✅ | 亲子场景刚需。**图片必须能配 caption**（语音/文字），裸图无 caption AI 只能瞎猜 |

### 不做

- **视频**：录视频本身就是重摩擦行为，违反产品哲学；80% 价值能用连拍 + 语音替代
- **手写/涂鸦**：手帐的"手写感"靠视觉设计还原（字体、纸质纹理），不是真让用户手写

### 二期待加

- **iOS/Android Share Extension**：从其他 app 接住内容（小红书心得、文章片段）。**架构上预留 `source` 字段**，进来的内容也是 Atom。

## 六、技术选型方向（暂定）

| 模块 | 推荐 | 理由 |
|------|------|------|
| **数据库** | Postgres + pgvector | 一套搞定关系+向量，运维简单 |
| **向量检索** | pgvector | MVP 阶段够用，等到了瓶颈再迁 Qdrant/Milvus |
| **LLM** | Claude Sonnet 4.6（开荒）+ Haiku 4.5（路由/接住） | 开荒用强模型保质量，实时路由用 Haiku 控成本 |
| **手机端** | 待定（React Native / Flutter / 原生） | 下次会话讨论 |
| **后端** | 待定 | 下次会话讨论 |
