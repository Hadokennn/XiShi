## 命名

### D0. 产品名 = 「夕拾」（Xishi）
- **决策时间：** 2026-05-03
- **理由：**
  - 取自鲁迅《朝花夕拾》，自带文化背书但不直接抄，只取后半截更含蓄、更品牌化
  - 完美对应产品节奏：白天扔（朝花）/ 晚上 AI 装订（夕拾）/ 睡前回看
  - 念起来 `xī shí` 轻、短、有余韵，logo 设计空间大（夕阳/手/花瓣均可）
  - 自带"温柔回望"情感，与亲子区、心情区氛围契合
- **影响：**
  - 产品对外名称统一用「夕拾」
  - **目录路径 = `XiShi/`**（与产品名一致，PascalCase）
  - 英文化候选：「Xishi」（拼音直译）/「Glean」（米勒《拾穗者》意象）
- **待办：** 上线前确认 App Store / 商标可用性

## 产品定位

### D1. 不做 chat agent，做手帐式第二大脑
- **决策时间：** 2026-05-03
- **理由：** chat 是线性流，context 易断；手帐是空间化图层，能沉淀。chat 是给你"问问题"的，手帐是给你"过日子"的。
- **影响：** UI 形态、AI 工作流、记忆架构都按"图层"设计，不按"对话"设计。

### D2. 异步为主，可手动触发生成手帐
- **决策时间：** 2026-05-03
- **理由：** 实时开荒成本高、可能打扰用户；异步装订有"翻手帐"的仪式感、更便宜；用户白天的目标是"扔进来不漏"，不是"立刻看到 AI 想法"。
- **影响：** 实时通路只做"接住"（确认收到、轻量分类），开荒留到晚上批处理。

### D3. MVP 只做 3 个分区：灵感 / 亲子 / 心情
- **决策时间：** 2026-05-03
- **理由：** 待办区市面太多、做不出差异化、稀释产品定位。MVP 跑通后再视情况补。
- **影响：** Zone 表系统初始化只插 3 条；UI 不预留待办入口。

### D4. 输入模态：语音 + 文字 + 图片
- **决策时间：** 2026-05-03
- **理由：**
  - 语音：核心场景命脉（半夜、陪孩子时双手不空）
  - 文字：精确表达 + 公开场合
  - 图片：亲子区刚需（孩子的画、表情、现场）
- **不做：**
  - **视频**：录视频本身重摩擦，违反产品哲学；80% 价值连拍 + 语音可替代
  - **手写/涂鸦**：手帐的"手写感"靠视觉设计还原，不是真让用户手写
- **二期：** iOS/Android Share Extension（架构预留 `source` 字段）

### D5. 家庭共享延后，但架构预埋钩子
- **决策时间：** 2026-05-03
- **理由：** MVP 复杂度已经够高；但家庭共享是未来差异化重点，不能锁死架构。
- **影响：** 所有内容实体用 `owner_id`（不是 `user_id`），未来加 `SharedAccess` 表即可。

### D6. 分享功能延后，但隐私字段预埋
- **决策时间：** 2026-05-03
- **理由：** 分享是用户粘性的重要手段，但脱敏分享的"度"需要打磨，不是 MVP 优先级。
- **影响：** 所有内容实体预埋 `privacy_level`、`contains_pii`、`redacted_content` 字段。

## 架构

### D7. 三层 Agent 架构（Concierge + 分区 Worker + 统一记忆层）
- **决策时间：** 2026-05-03
- **理由：** 直接把分区做成强隔离 subagent 会撞上"跨分区/跨天关联"命门。分区只承载"加工动作"（人格、prompt、开荒模式），记忆是全局的。
- **影响：** 分区 Worker 设计为无状态服务；Concierge 是唯一调度入口。

### D8. 五层记忆模型（Buffer / Today / Zone / Episodic / Soul）
- **决策时间：** 2026-05-03
- **理由：** 按"时间衰减 × 内容性质"两维度切，不按单一"内容性质"切。Episodic 是育儿场景命脉，普通日记 app 没这层。
- **影响：** 见 [architecture.md](architecture.md) 二节。

### D9. 分区开荒模式按场景定制，不通用
- **决策时间：** 2026-05-03
- **理由：** 不同分区的目标完全不同——灵感要扩展、亲子要追问、心情要陪伴。通用 prompt 会把所有场景拉成最低公约数。
- **影响：**
  - 灵感区 = **拓展 + 关联**
  - 亲子区 = **苏格拉底式追问**
  - 心情区 = **共情 + 镜像**（**红线：不给建议**）

## 数据模型（细节见 data-model.md）

### D10. Atom 永不真删除（soft delete）
- **理由：** prompt/模型升级后能重新开荒。原始数据 = 单一权威源（SSOT）。

### D11. `event_time` ≠ `created_at`，必须分开
- **理由：** 核心场景是"晚上记白天事"。混用会让事件时间线全乱。

### D12. 一条 Atom 可属多个 Zone（zone_ids 是 array）
- **理由：** "我想给孩子做识字 app" 同时是亲子+灵感+待办。强行单选要么 AI 选错、要么用户被迫拆分（违反低摩擦）。

### D13. Episode 是独立实体，不是 Atom 的字段
- **理由：** 一个事件可由多条 Atom 拼成；Episode 是用户 confirm 过的高质量长期记忆，独立索引；未来家庭共享时 Episode 是共享单元。

### D14. Episode 生成时机 = 混合模式（C 选项）
- **理由：** AI 默认草拟 Episode（status=draft），但**只在用户主动进入"事件复盘"页面时才显示**——日常手帐不打扰。

### D15. Soul 必须 propose → accept，可追溯
- **理由：** AI 偷偷写 Soul 是信任灾难。`evidence_atom_ids` 让用户能追问"凭啥这么说我"。

### D16. Soul 有半衰期：3 个月没确认会弱化或提醒 review
- **理由：** 人会变。一条 Soul 半年前是真的，半年后可能就不准了。

### D17. Soul Review 时机 = 每周日晚
- **理由：** 周日晚有自然的"回顾本周"心境；频率不打扰；批量 review 比逐条确认效率高。

## 技术选型（暂定，开始实现时确认）

### D18. 数据库 = Postgres + pgvector
- **理由：** 一套搞定关系+向量；运维简单；MVP 阶段够用；性能瓶颈再迁 Qdrant/Milvus。

### D19. LLM Provider 策略：主线 Kimi K2（OpenAI 兼容）+ Anthropic 作为对比与备选
- **决策时间：** 2026-05-12（修订自原 D19）
- **原决策（已废弃）：** Claude Sonnet 4.6（开荒）+ Haiku 4.5（路由/接住）
- **修订理由：**
  - **成本**：Kimi K2 价格约为 Anthropic 的 1/5，MVP 自用 + 夜间装订批处理对账单友好
  - **学习覆盖面**：OpenAI 兼容协议 = 一套 schema 通吃 DS / Kimi / 智谱 / 通义 / 阶跃 / 本地 vLLM，国内 Agent 岗主流
  - **Agentic 能力**：Kimi K2（2025）在 tool use / 中文 / 长上下文（200k）已达国产第一梯队
  - **简历分量**：Agent 系统含金量在自己实现的 Concierge / 分区 / 五层记忆 / Soul，与底层 provider 无关
- **影响：**
  - 主线代码用 `openai` SDK + `base_url=https://api.moonshot.cn/v1`
  - D3 学习仍 dump 一次 Anthropic 响应做对比，建立跨 provider 肌肉记忆（OpenAI chat completions vs Anthropic content blocks）
  - 装订手帐的 batch worker 在成本敏感时可切到 DeepSeek（DS 也是 OpenAI 兼容，改 base_url 即可）
- **未做：** **不预先抽象 LLMClient 协议**——D3 先 hardcode Kimi 跑通，W2 service 层稳定后再抽，避免过度设计（违反"简洁优先"红线）

## 红线（永远不做）

- ❌ **心情区给建议** —— 违反产品哲学，会让用户崩溃
- ❌ **AI 偷偷写 Soul** —— 信任灾难
- ❌ **修改/删除原始 Atom 的 content** —— 破坏单一权威源，永远无法重新开荒
- ❌ **手写/涂鸦输入** —— 不是这个 app 该解决的问题
- ❌ **录视频输入** —— 违反低摩擦输入哲学
