## 概念巩固

### 一、Pydantic v2 真正用起来

#### BaseModel + Field + model_validator

```python
from typing import Literal
from pydantic import BaseModel, Field, model_validator

ZoneId = Literal["inspiration", "parenting", "mood"]

class RouteResult(BaseModel):
    primary_zone_id: ZoneId
    zone_ids: list[ZoneId] = Field(min_length=1)
    zone_confidence: dict[ZoneId, float]
    reasoning: str = Field(min_length=1)

    @model_validator(mode="after")
    def _check_invariants(self) -> "RouteResult":
        if self.primary_zone_id not in self.zone_ids:
            raise ValueError(...)
        return self
```

#### 关键认知

- **`Literal` 当枚举用**：比 `str` + 单独写 enum 类简洁，且 LLM 输出的字符串能直接被 Pydantic 校验
- **`mode="after"`**：所有字段都 parse 完之后跑——可以放跨字段约束（primary 必须在 zone_ids 里）
- **`mode="before"`**：在字段类型转换前跑——用于数据预处理（D4 没用到）
- **`model_validate(dict)` vs `model_validate_json(str)`**：前者吃 dict，后者直接吃 JSON 字符串。我们 `_parse` 用前者，因为 strip_fence 后已经是 dict 来源

#### 跟 JS 生态对比

- Pydantic ≈ Zod（运行时 schema 校验），不是 TS（编译期类型）
- `model_validator` ≈ Zod 的 `.refine()`
- `Field(min_length=1)` ≈ Zod 的 `.min(1)`
- 区别：Pydantic 跟 Python type hint 深度绑定，IDE/mypy 顺带满足；Zod schema 独立于 TS 类型

### 二、`response_format=json_object` 模式

#### 是什么

OpenAI 协议提供的"JSON 模式"——模型保证输出**合法 JSON**（不带任何 markdown fence、不带 prose），但**不保证 schema 匹配**。

不同于 OpenAI 独家的 `response_format={"type":"json_schema","strict":true}`——那个保证 schema，但 Kimi/DS 都不支持。

#### D4 实测观察（observe-before-implement）

6 次调用（Kimi + DS × 3 类输入），全部：
- ✅ 不塞 ```json fence
- ✅ 字段名一字不差
- ✅ JSON 解析全成功
- 🟡 Kimi 在跨分区时主动给非 zone_ids 的分区也分配低 confidence（`{mood: 0.1}` 当软标注）—— 我把 schema 设计成 zone_confidence key 集合可以**超过** zone_ids，刚好兼容

#### 为什么仍写 fence-strip + retry

零代价的防御：
- 未来 temperature 调高 / 长 prompt / 模型升级时可能开始塞 fence
- retry 把上次错误带回 prompt 让模型自纠——这是 staff 级 Agent 常规操作

#### 跟 tool_use 路由的差异（留 W3 验证）

| 维度 | json_object | tool_use |
|---|---|---|
| Schema 保证 | ❌（要自己 Pydantic） | ✅ 协议层保证 |
| 跨厂商支持 | ✅ Kimi/DS/OpenAI 都支持 | 🟡 Kimi 支持，DS 不太稳 |
| 心智成本 | 低 | 中（要写 tool spec） |
| 适合场景 | 单次结构化输出 | 多轮决策、Agent 循环 |

### 三、Typer 子命令与 async

`@app.command()` 装饰的函数**不能是 async**——Typer 是同步框架。所以 CLI handler 写法：

```python
@app.command()
def route(text: str, model: str = "kimi") -> None:
    result = asyncio.run(svc_route(text, model=model))  # 同步壳调异步 service
    ...
```

每个 CLI 命令都自己 `asyncio.run`——这是有意为之，service 层不感知谁在调（CLI/FastAPI/cron 都能复用）。

未来如果想跨命令共享 event loop（如批量），就用 Typer 的 callback 起 loop，再 `asyncio.run_until_complete`。但 D4 不需要。

## 面试拷问准备

### 「你为什么不用 tool_use 路由？」

- json_object + Pydantic 是双方协议明文支持的最稳路径
- tool_use 协议细节是 W3 学习重点，故意分开以保证讲深度
- W3 之后我能展示**同一个 route 任务，json_object 和 tool_use 两种实现的代码 + raw + trade-off**

### 「retry 机制为什么不无限重试？」

- 重试不是错误处理银弹——LLM 失败常常是 prompt 问题，不是抖动
- 一次 retry 把"上次错在哪"带回去触发模型自纠，第二次还错说明 prompt 或 schema 本身有问题，应该让上层感知（raise）
- 无限重试会把 cost 和延迟都打飞

### 「为什么 zone_confidence 的 key 集合允许超过 zone_ids？」

- Observe 时发现 Kimi 主动给"非主分区"也分配低 confidence（当软标注）
- 强制 == 会让模型 retry 没必要的次数
- 软标注其实是个**有用信号**——比如"主分区是亲子但 mood: 0.3"暗示用户情绪受影响，未来可以作为 episode 关联线索
