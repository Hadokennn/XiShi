## 核心 observe 发现（observe-before-implement）

跑 `experiments/observe_stream.py --real kimi,ds` 看到 Kimi 和 DS 的 SSE chunk 方言差异：

| 维度 | Kimi | DeepSeek |
|---|---|---|
| chunk 数（短输入 40 字回复） | 21 | 29 |
| chunk 数（中输入 200 字回复） | 114 | 203 |
| `finish_reason='stop'` 在第几个 chunk | 倒数第 2 | 最后 |
| 是否有 trailing chunk（`choices=[]`） | ✅ 有 | ❌ 无 |
| 最后有效 chunk 的 `delta.content` | `None` | `''` |
| usage 字段位置 | delta.usage（嵌套）+ trailing 顶层 | 最后 chunk 顶层 |
| 首字延迟（短输入） | 较慢（~0.5s） | 较快（~0.2s） |

**两个会咬人的陷阱**（如果不 observe 直接写 `chunk.choices[0].delta.content`）：

1. **Kimi trailing chunk IndexError**：盲取 `choices[0]` 会炸。必须先 `if not chunk.choices: continue`
2. **`if delta.content` vs `if delta.content is not None`**：
   - Kimi 最后有效 chunk 的 `delta.content = None`
   - DS 最后有效 chunk 的 `delta.content = ''`
   - 用 `if delta.content:` 两者都能干净跳过

→ `ask_stream()` 最终 5 行核心循环：
```python
async for chunk in stream:
    if not chunk.choices:
        continue
    delta = chunk.choices[0].delta
    if delta.content:
        yield delta.content
```

如果不先 observe，至少要踩一次 IndexError + 一次"为什么最后一个 chunk content 是 None"才能写对。observe-before-implement 规则今天直接救命。

## 概念巩固

### 一、Server-Sent Events (SSE) 协议本质

#### 一句话

SSE 是 HTTP 的"服务器单向流式推送"——客户端发起一个 GET / POST，服务端**不关闭连接**，按 `text/event-stream` 协议持续推 `data: <chunk>\n\n` 直到结束。

#### 跟 WebSocket / 长轮询的区别

| 机制 | 双向 | 协议复杂度 | 客户端断线重连 |
|---|---|---|---|
| **SSE** | ❌ 服务端→客户端单向 | 极简（HTTP + 几行格式约定） | 浏览器原生支持 `EventSource` 自动重连 |
| **WebSocket** | ✅ 双向 | 升级握手 + 帧协议 | 自己写 |
| **长轮询** | 模拟双向 | 应用层 | 自己写 |

LLM 流式天然单向（客户端发 prompt → 服务端流回 token），SSE 完美匹配。所有 OpenAI 兼容 API（含 Kimi/DS）都用 SSE 推 chunk。

#### 看到的 chunk wire 格式

观察 OpenAI SDK 时 SDK 已经把 SSE 解析成了 `ChatCompletionChunk` 对象，但底层 wire 长这样：

```
data: {"id":"...","choices":[{"delta":{"content":"因为"},"finish_reason":null}]}\n\n
data: {"id":"...","choices":[{"delta":{"content":"阳光"},"finish_reason":null}]}\n\n
data: [DONE]\n\n
```

每行 `data: <json>` 是一个事件；空行作分隔；`[DONE]` 是 OpenAI 协议约定的流结束信号（DS 用这个，Kimi 也用）。

#### 跟 JS 生态的对应

| 概念 | Python | JS |
|---|---|---|
| 异步迭代 | `async for chunk in stream` | `for await (const chunk of stream)` |
| 流结束信号 | `[DONE]` SDK 内部消化 | `EventSource` `onmessage` 自然停 |
| 中途取消 | 关闭 client / break out of for-loop | `eventSource.close()` |

### 二、Python AsyncIterator

#### 类型签名

```python
from collections.abc import AsyncIterator

async def ask_stream(...) -> AsyncIterator[str]:
    ...
    async for chunk in stream:
        yield ...   # 注意：是 yield，不是 return
```

#### 关键认知

- `async def` + `yield` = **async generator function**——调用它返回一个 async generator（实现了 `__aiter__` / `__anext__`）
- 必须用 `async for` 消费，不能用普通 `for`
- 跟 sync generator 的不同：`__anext__` 是 coroutine，每次取值都可能 await（IO）

#### 为什么 service 层契约用 `AsyncIterator[str]` 而不是 `List[str]` 或回调

| 选项 | 缺陷 |
|---|---|
| `List[str]`（一次性返回） | 退化为非流式，失去 TTFT 优势 |
| 回调函数 `on_chunk: Callable` | service 层感知调用方 → 违反"service 不感知谁在调"契约 |
| **`AsyncIterator[str]`** ✓ | 调用方决定怎么消费（写 stdout / SSE / WebSocket / 累加成字符串），service 只产 token |

### 三、Typer 同步外壳吃 async iterator

#### 问题

```python
@app.command()
async def ask(text: str) -> None:   # ❌ Typer 不支持 async 命令
    async for chunk in ask_stream(text):
        ...
```

Typer 是同步框架，`@app.command()` 装饰的函数必须是普通 `def`。

#### 解法对比

| 方案 | 代码 | 优缺点 |
|---|---|---|
| A. 命令内 `asyncio.run` | `def ask(text): asyncio.run(_inner(text))` | 每命令重复样板 |
| B. helper 函数 ✓ | `def ask(text): _stream_to_stdout(svc_ask_stream(text))` | CLI handler 一行，helper 集中处理 KeyboardInterrupt |
| C. typer-async 第三方包 | 加依赖 | YAGNI |

选 B。`_stream_to_stdout` 内部 `asyncio.run(_drain())`，捕获 `KeyboardInterrupt` 返回 exit code 130（Unix 约定 SIGINT），已显示内容不丢。

#### 为什么 exit code 130

Unix 约定：`128 + signal_number`。SIGINT 是 2，所以 ctrl+c 退出码是 130。脚本管道里可以根据 130 判断"用户主动中断" vs 错误。

## 面试拷问准备

### 「为什么 ask 流式，route 不流式？」

四维框架（输出长度 / 结构化要求 / 下游消费者 / 延迟敏感度），不是拍脑袋。ADR-0002 有详细论证。可以追问到 route 的 "Pydantic 校验在哪一步发生"——答：完整 JSON 收齐后 `model_validate`，partial JSON 解析不值这个复杂度。

### 「跨 provider 流式协议有什么坑？」

- 答 chunk 数差异（Kimi/DS 中输入 114 vs 203）
- 答 trailing chunk（Kimi `choices=[]` 会让 `chunk.choices[0]` IndexError）
- 答 `delta.content` 的 None vs `''` 差异
- 答 finish_reason 在不同位置（Kimi 倒数第 2，DS 最后）

### 「SSE 和 WebSocket 怎么选？」

LLM 流式是天然单向（服务端→客户端），SSE 完美匹配且协议极简。WebSocket 是过度设计——除非未来要做"客户端实时打断模型"这种双向交互（W4 Concierge 主循环可能用得到，那时再说）。

### 「Ctrl+C 中断为什么是 exit 130？」

Unix 约定 `128 + signal_number`，SIGINT=2，所以 130。脚本管道里能精确区分"用户主动中断" vs "错误"。
