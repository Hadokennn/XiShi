## prompt v2 设计逻辑

### v1 → v2 改动

| 维度 | v1 | v2 |
|---|---|---|
| few-shot 数 | 3 | 5 |
| 跨 3 分区案例 | ❌ | ✅ "陪小宝玩积木，想到空间感 app，但又累" → inspiration 主 + mood + parenting |
| 心情主带亲子要素 | ❌ | ✅ "小宝哭 20 分钟，我真的好烦躁" → mood 主 + parenting 副 |
| 判断原则数 | 4 条 | 5 条（加「主分区跟用户叙述焦点，不跟事件类型」） |
| token 增量 | 基准 | +~250 tokens / 次（W6 caching 后会被缓存掉） |

### 关键设计点：「叙述焦点」边界

- **"小宝今天因为关电视哭了 20 分钟"** → parenting 主（叙述焦点是孩子行为事件）
- **"小宝今天因为关电视哭了 20 分钟，我真的好烦躁"** → mood 主 + parenting 副（叙述焦点切到自己的情绪）

这两条对照案例**显式教给模型**：主分区不是事件类型决定的，是用户用什么作主语决定的。batch 测试时两家模型立刻 internalize 了这个规则——证明 few-shot 5 例数量足够，不需要堆到 10 条。

### batch 测试关键发现

```
[焦点=事件] 小宝今天因为关电视哭了 20 分钟
  [kimi]  ► parenting 0.90
  [ds]    ► parenting 0.90  | + mood 0.50

[焦点=自己] 小宝今天因为关电视哭了 20 分钟，我真的好烦躁
  [kimi]  ► mood 0.85  | + parenting 0.70
  [ds]    ► mood 0.85  | + parenting 0.70
```

- **两家主分区切换完美对齐**（事件 → 自己叙述时 primary 切到 mood）
- 唯一分歧：纯事件描述时 DS 多识别出"哭"的隐含情绪（mood 0.50 副标）。这种**风格差异**是好事——投递时可以讨论"两家模型对隐含情绪的敏感度差异"
- 跨 3 分区案例两家都正确识别 3 分区，confidence 排序也合理

### 三层切分契约

| 层 | 文件 | 职责 | 不感知 |
|---|---|---|---|
| **入口层** | `cli.py` | 解析参数 / 格式化输出 / 处理 KeyboardInterrupt | 业务逻辑 / LLM / DB |
| **service 层** | `service/*.py` | 领域函数（异步） / 跨调用方复用 | 谁在调（CLI/FastAPI/cron） |
| **数据层** | `schemas/*.py` | Pydantic 校验契约 | 持久化 / IO |
| **prompt 层** | `prompts/*.py` | system + few-shot + build_messages | LLM 客户端细节 |

`_client_for()` 跨 service 共享（D5 复用 D4 设计），future capture / bind 直接复用——这是 D19 决策「不预先抽象 LLMClient 协议」的红利：水平复用靠模块，不靠继承。

## W1 末 self-check 草稿

按 roadmap §八「每周末 30 分钟自检」，下面三个问题先草拟，D7 正式自检时校准。

### 问题 1：W1 三个核心概念，能不能一句话讲清楚原理 + 一句话讲清楚 trade-off？

| 概念 | 原理一句话 | trade-off 一句话 |
|---|---|---|
| **async/await** | 单线程事件循环靠 IO 等待时让出执行权，让其他 coroutine 同时跑 | 解决 IO 并发不是 CPU 并发；同步调用混进来卡死全部，所以 DB 要 asyncpg 不是 psycopg2 |
| **Pydantic v2** | 用 Python type hint + 装饰器在运行时校验数据契约，跨字段约束走 `@model_validator` | 跟编译期 mypy 互补但不重叠；BaseModel 创建有运行时开销，热路径上要谨慎 |
| **Typer CLI + service 分层** | CLI handler 只解析参数 + 调 service + 格式化；service 异步函数不感知调用方 | service 不暴露 IO 细节给 CLI = 多写一层桥接（`_stream_to_stdout`），换 W2 加 FastAPI 时零返工 |
| **流式 SSE**（D5 偷跑） | 服务端 HTTP 不关连接，按 `data: <json>\n\n` 持续推 chunk 到 `[DONE]` | LLM 单向天然契合 SSE；但跨 provider 协议方言多（Kimi trailing chunk、delta.content None vs ''），observe-before-implement 是必须 |

## 概念扩展：「mock 是债不是省事」

ADR-0003 决策 2 拒绝了 JSONL Buffer mock 中间态——这是个跨语言通用的工程原则，单独抽出来强调：

**Mock/中间态的真实成本**：
1. 写一遍 → 用一遍 → W2 写真实版再用一遍 = 写了两遍
2. 类型/字段 schema 必有微妙差异（JSONL 字符串 vs PG UUID/timestamp），迁移时所有 caller 改一遍
3. 中间态进 git history 后，未来读者会以为"故意分层"，加重维护心智
4. **唯一例外**：当真实实现的成本是 mock 的 10 倍以上（跨多周、跨服务）才考虑 mock

夕拾的场景：JSONL mock 100 行 vs Postgres 实现 150 行 → 差异不到 2 倍，直接上真东西。
